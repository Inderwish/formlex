# 插件验证范围

插件与项目版本为 1.4.0；HTTP API v4、种子版本 4、1,424 条词库及用户数据格式保持兼容。

## 自动验证

运行 `pwsh -NoProfile -File scripts/package-plugin.ps1`：

1. 从主项目源码生成插件运行副本，再逐文件比较内容。
2. 生成 ZIP 并解压到临时目录，以解压版作为独立 CLI 的测试来源。
3. 运行 32 项 Node 内置测试，包括原有 26 项及 6 项插件测试。
4. 检查所有插件文件前后 SHA-256，确认执行过程没有写入安装目录；子进程设置超时，测试服务使用临时数据并关闭。
5. 检查成功后才替换交付 ZIP，清理临时目录，打印 `DONE`。

验证覆盖默认八维、随机 2–3 条、全部主题冷暖范围、独立特色 1–5 条、锁定与单维重抽、显式冲突与自由模式、失效 ID、UTF-8/BOM/超大文件、工作台的个人词库与编辑词条、HTTP/MCP 查询一致性、共享历史、保存失败、快照稳定及连接中断的未知保存状态。原有测试继续覆盖空库、无组合、搜索上限、迁移和重启。

发布时另用 Codex 的 plugin-creator 校验器检查插件清单与资源，用 skill-creator 校验器检查 Skill 格式。插件无自动 MCP 配置、没有个人数据或本机用户路径，资源路径均位于插件内部。

## Skill 执行边界走读

以下是对实际 Skill 指令的场景走读，用于检查交付范围和优先级；不是对多个模型的成功率评测，也不保证每次设计都达到相同审美结果。

| 用户请求 | 应采取的路径 | 已核对的边界 |
| --- | --- | --- |
| “大胆重构当前前端，保留业务功能” | 读取项目及现状 → 离线抽取 → 确定主导方向与区域 → 改布局/排版等主要视觉结构 → 实现和检查。 | “先判断交付范围”明确要求实现完成；简报不产生额外审批；业务流程、路由和数据含义保留。 |
| “只给三个方案，不改代码” | 按需查询与抽取，为三个方向分别给出配色、布局、字阶与应用区域。 | 只输出设计简报，代码不修改；不因 Skill 的默认实现工作流越过用户范围。 |
| “必须保留品牌蓝 #1246A0、现有字体与 React” | 将品牌与技术作为硬约束，筛选候选，优先通过构图、留白和层级建立变化。 | 抽到的词条是参考数据；明确的品牌、技术与局部范围优先，不能用随机结果覆盖。 |

三个路径均按需查询摘要与少量术语，不把完整词库注入上下文。鼠标、持续动效及三维线索需要对应触控、静态或减少动态替代。纯后端及非视觉修复不进入该 Skill。

## 未自动执行的安装操作

验证不添加当前机器的 marketplace、不安装全局插件、不修改 MCP 配置、不启动常驻服务。安装说明中的 marketplace 与 MCP 命令已按当前 Codex CLI 帮助核对；清单通过格式与资源校验，但没有宣称已在用户的插件页完成安装。需要用户按安装说明自行添加来源和安装。
